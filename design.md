# Design System

Two distinct visual layers live in this app, and they're deliberately not
styled the same way:

1. **App chrome** — the dark editor UI you work in (`#topbar`, `#editorPane`,
   tabs, buttons, toasts). Never appears in an export.
2. **Document design** — the actual branded output (`.doc-page` and
   everything inside it). This is what gets exported to PDF/DOCX/HTML, so it
   has to look right on paper, not just on screen.

All of it lives in `src/renderer/styles.css`.

---

## Document design tokens

These are the brand colors — the ones that end up in exported files, so
changing them changes what clients see.

| Token | Hex | Used for |
|---|---|---|
| Navy | `#0D1117` | Headings, table headers, primary text |
| Deep Navy | `#1C2333` | Body copy |
| Blue | `#1A5BFF` | Accent — section numbers, links, totals, pills |
| Slate | `#EDF0F8` | Cover page background |
| Stone | `#6B7280` | Muted/secondary text |
| Border | `#D1D8E8` | Table borders, dividers |
| Blue Tint | `#EBF0FF` | Alternating table rows, callout fills |
| Dot | `#C2CEE8` | Cover page dot-grid texture |
| White | `#FFFFFF` | Page background |

One extra color outside the token set: `#E8A93B` / `#FFF8E8` (amber) for the
`EXAMPLE` callout, kept visually distinct from the blue `NOTE` callout.

**Fonts:** Bebas Neue (headings, wordmark, section titles — the loud one) +
Inter (body copy, labels, tables — weights 300–700, mostly 300 for body text
and 600–700 for anything that needs to stand out).

## App chrome tokens

The editor itself is dark, deliberately unrelated to the document palette —
it should never be mistaken for the thing you're producing.

| Token | Hex | Used for |
|---|---|---|
| App BG | `#0B0E14` | Window background |
| App Panel | `#12161F` | Topbar, editor pane |
| App Panel 2 | `#161B26` | Inputs, buttons, badges |
| App Line | `#232938` | Borders/dividers in the chrome |
| App Text | `#C9D2E3` | Default UI text |

Preview area sits on `#1a1d24` (darker than the panels) so the white
`.doc-page` reads as a sheet of paper floating in a dark workspace, with a
`box-shadow` giving it lift.

## Layout

```
#app (column)
├── #topbar          brand · file label · action buttons · page count
└── #body (row)
    ├── #editorPane   42% width, 320–720px clamp
    │   ├── #editorTabs        Document Info / Content / Guide
    │   ├── #metaForm           cover page fields
    │   ├── #editorWrap         raw DSL textarea (monospace)
    │   └── #helpPanel          syntax reference, scrollable overlay
    └── #previewPane   flex:1, scrolls independently
        └── #previewInner       210mm wide, mirrors the real export
```

The editor and preview are two honest panes, not a WYSIWYG blend — what's in
`#previewInner` is generated by the same render path used for HTML export, so
what you see really is what you get.

## Document page anatomy

Every page is `210mm × 297mm` (A4), matching the PDF export exactly so the
on-screen preview never lies about pagination.

- **Cover page** (`.doc-cover`) — dot-grid texture background, kicker label,
  Bebas Neue wordmark + title, description, and a metadata row along the
  bottom (client / date / version, whatever the Document Info tab holds).
- **Content pages** (`.doc-content`) — a run header (brand + doc title,
  repeats on every page like a real letterhead) and a footer with page
  numbers, both absolutely positioned so they survive pagination.
- **Section heading** (`h1.sec`) — big Bebas Neue number in blue + title in
  navy, underlined. Always starts a fresh page (see `PAGEBREAK` behavior in
  the parser).
- **Sub-heading** (`h2.sub`) — smaller, blue, no page break.

## Component patterns (inside a document)

Each DSL block in the README maps to exactly one CSS component, styled to
read as part of a coherent printed report rather than a web page:

| Block | CSS | Visual idea |
|---|---|---|
| `NOTE` | `.callout` | Blue left rule, blue-tint fill |
| `EXAMPLE` | `.example` | Amber left rule, cream fill (only non-brand color) |
| `TABLE REQ/DATA/PRICE` | `table.reqtable` etc. | Navy header row, alternating tint rows, numeric columns auto right-aligned |
| `TOTALS` | `.totals` | Right-aligned mini table, bold grand-total row with a rule above it |
| `CARDS` | `.cardgrid` / `.card` | Bordered boxes, wraps responsively |
| `STEPS` | `ol.steps` | Numbered circular badges (navy fill, counter-based, not manual numbering) |
| `BULLETS` | `ul.bullets` | Small blue dot, not a default browser bullet |
| `GLOSSARY` | `dl.gloss` | Term/definition pairs |
| `SIGNATURE` | `.siggrid` / `.sigbox` | Side-by-side signature lines |
| `PILL` | `.pill` | Small navy rounded label above a table |
| `DIAGRAM` | `.doc-diagram` | Mermaid SVG, scaled to fit page width |
| `IMAGE` | `.doc-figure` | Centered, capped width, caption below |
| Table of Contents | `.toc-row` | Dotted leader between number/title, generated from headings — never hand-authored |

The rule threading all of these together: **every visual distinction maps to
a semantic block**, not a one-off style. If you want a new visual treatment,
it should come with a new DSL block in `parser.js`/`render.js`, not a class
bolted onto an existing one.

## Interaction feedback

- **Unsaved changes** — a blue dot (`.dirty`) next to the filename; clears on
  save. No modal, no "are you sure" — the dot is the whole affordance.
  Same underlying "does this match what's on disk" state also feeds
  `beforeunload` if that's ever wired in.
- **Toasts** (`.toast`) — bottom-right, slide up + fade in, dark by default,
  red-tinted (`.error`) for failures. Used for save/open/export confirmations
  and page-count changes — anything that happens without a visible result on
  screen otherwise.

---

## Why two systems, not one

It would be simpler to reuse one palette for both the editor and the
document. Deliberately not doing that: the editor's dark chrome is a tool you
live in for hours and should recede; the document is the deliverable and
needs to look identical whether it's on screen, printed, or opened in Word.
Coupling them would mean a "make the editor prettier" change risks changing
what ships to a client, which is the wrong failure mode for this app.
